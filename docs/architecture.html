1. Scale strategy: 500,000 startups, products and papers without manual intervention

Structured first, LLM last. The cost of a record is dominated by how it is extracted. All three bulk verticals in the trial are collected from machine channels, with no LLM call: YC company pages embed the full company object as JSON; Futurepedia publishes sitemap_tools.xml and a JSON payload per tool; OpenRouter and the Hugging Face, arXiv and GitHub APIs are JSON. At 500k this matters twice: an LLM call costs ~1,000× an HTTP fetch, and structured parsing cannot hallucinate. The LLM chain is the fallback for long-tail pages (vendor "about" pages, job posts without JSON-LD).

Frontier, then fetch. Each source is a BulkSource(discover, fetch, key_of): discover is cheap (one sitemap or index call yields thousands of URLs), fetch turns one item into records. The engine (pipeline/bulk.py) runs a bounded worker pool, writes in batches, and is resumable: items whose key is already stored are skipped, so a crash or a deploy costs nothing. One bad page never kills a run; failures are counted by reason. Measured on one laptop process: 2,233 YC pages in 447 s (0 failures, polite 5 req/s); 2,431 Futurepedia pages plus ~2,400 vendor homepages for maker lookup in 787 s; 1,138 papers with live stars via GitHub GraphQL (100 repos per call).

Scaling out without code changes. Throughput is bounded per host (politeness), not per machine, so scale comes from many sources in parallel and more workers, never from hitting one site harder:

  • Queue: the in-process frontier becomes a shared queue (Redis Streams / SQS) with visibility timeouts. Workers are stateless containers. The keyed upsert makes duplicate delivery harmless (at-least-once delivery, exactly-once records).
  • Shared per-host state: politeness intervals, rate-limit pauses, anti-bot tier and circuit state move from process memory to Redis keyed by host, so 50 workers behave like one polite client per site.
  • Separate pools by cost: HTTP workers (cheap, high concurrency), browser workers (~50× cost, fed only URLs whose host is on the browser tier), LLM workers (bounded by provider token budgets). Each autoscales on its own queue depth.
  • Raw capture: fetched HTML is written to object storage (S3) keyed by URL and date, so schema changes or a better extractor re-run over stored pages, not over the web.
  • Arithmetic: 500k records ÷ 30 sources ≈ 17k pages per source. At a polite ~3 req/s per host that is ~90 req/s overall (~5.4k pages/min): 500k pages in about 1.5 h with sources in parallel. Fetching is I/O-bound, so a handful of async processes is enough; the browser and LLM pools are what grow with the share of long-tail pages.

2. Handling 413s and 429s across thousands of concurrent extractions

413 / context overflow: never send what will not fit

  • Budget per provider (Gemini 30k, Groq 6k, DeepSeek 24k input tokens; configurable), counted with tiktoken ×1.1 safety margin, plus a hard byte cap (200 kB), because some gateways reject on bytes before tokens are counted.
  • Chunker ("head + densest blocks"): strip boilerplate; lift metadata to the top (title, meta, JSON-LD, <time>); if over budget keep the head (~30%), score the remaining blocks for density (schema keywords, numbers, dates, proper nouns; menus and link farms penalised), take the best greedily, restore original order.
  • If a 413 still happens (a provider's real limit is lower than documented): shrink the budget ×0.55 and retry the same provider, up to 3 times, then fall through to the next provider.

429: rarely hit one, recover cleanly when it happens

  • Client-side token buckets per provider: requests/min and tokens/min. A call reserves (1 request, N tokens) before sending, so the fleet stays under quota instead of discovering it.
  • On 429: pause that provider's limiter for everyone, exponential backoff with full jitter, honouring Retry-After and Gemini's retryDelay. After 2 tries the provider enters a 90 s cooldown and the request falls through the chain.
  • Other errors: 5xx and timeouts retry with backoff; 401/403/404 disable the provider; invalid JSON, schema or ungrounded identity get one repair call, then fall through.

At thousands of concurrent extractions the same interfaces become distributed: buckets move to Redis (GCRA / redis-cell, one atomic call per reservation) so all nodes draw from one budget per API key; the extraction queue gives backpressure (workers only pull when a bucket can pay); keys are sharded across accounts where terms allow; priority lanes keep a fresh-news extraction from waiting behind a bulk backfill. The grounding gate runs on every result: grounded fields must appear in the source text (fuzzy match ≥ 85), otherwise they are nulled, and an ungrounded identity field rejects the record. A dropped record is preferable to an invented one.

3. Freshness tracking: never processing the same article or job twice across nodes

Proving "< 24 h". Dates are read from the strongest available evidence, in rank order: JSON-LD datePublished/datePosted (0.95), meta tags (0.9), <time> (0.8), URL date (0.6), byline (0.55), Last-Modified (0.3). Modified/updated dates are never used. Relative dates ("2 hours ago", "3d") are resolved against fetch time, and every date keeps its precision ("yesterday" is a 24 h interval, not an instant). The verdict is three-valued: FRESH and STALE require proof; UNCERTAIN items are not ingested. Undated items use two heuristics: listing bracketing (an undated item above a fresh dated item in a verified reverse-chronological list is fresh) and new since last run (a URL never observed before, above the first known URL, appeared after the previous run, which ran within the window). Cold start or a gap longer than the window means UNCERTAIN.

4. Storage strategy

StoreRole and justification
PostgreSQL (primary)System of record. One table per entity type with typed columns for what is queried (name, domain, dates, stars) plus a JSONB body for the full record, a unique natural key for idempotent INSERT…ON CONFLICT DO UPDATE, and time partitioning for news/jobs. It gives transactions for the claim/lease protocol, mature tooling, and comfortably holds 500k–50M rows on one primary with read replicas. The trial's SQLite RecordStore has the same interface (keyed upsert, JSON body), so the swap does not change callers.
pgvector (in Postgres)Embeddings of descriptions, abstracts and job texts for semantic search, "similar startups", and candidate generation in entity resolution. At this scale an HNSW index inside Postgres avoids running a second database and keeps vectors joinable with records. A dedicated vector DB is warranted only well beyond ~10M vectors or for heavy filtered-ANN workloads.
Graph layerRelationships (startup–product, startup–founder, paper–repo–org, job–company, news–mentions) are first stored as typed edge tables in Postgres, keyed by canonical entity id, and queried with joins and recursive CTEs, which covers 1–2-hop questions. When multi-hop traversal and graph algorithms (investor networks, talent flow, influence) become core, the same edges are streamed (CDC) into Neo4j or Memgraph as a read model; Postgres remains the source of truth.
RedisCoordination, not data: work queues, leases, distributed token buckets, per-host politeness and circuit-breaker state.
Object storageRaw HTML/JSON snapshots (compressed, keyed by URL and fetch date), for audit (every value traces to a captured page), re-extraction, and evaluation sets.

5. Entity resolution and protected sources (summary)

Entity resolution is deterministic and evidence-ranked: website domain > exact name > legal-suffix-stripped ("OpenAI, Inc.") > spacing and punctuation ignored ("Open AI") > scraping noise removed > generic words removed (distinctive keys only) > guarded fuzzy match (ratio ≥ 92, same first letter, 4-point margin). Names that match no seed become new canonical entities, clustered with typo merging. Merging is blocked when two names each come with their own, different website (YC lists both "Caire Health" and "Cair Health") or differ only in digits. A startup's own website is identity evidence: YC's "Cohere" (cohere.io) is not the seed Cohere (cohere.com). Batch resolution is order-independent (tested by shuffling); every mapping is logged with method, score and an example source URL.

Protected sources are handled by classification, not evasion. Responses are classified (Cloudflare challenge or block, DataDome, AWS WAF CAPTCHA, empty JavaScript-only page). JavaScript-only pages and non-interactive challenges are rendered in real Chromium (sticky per host). CAPTCHAs and hard blocks are never solved: the host's circuit opens (probe-first, so a wall is hit once) and the pipeline uses the site's machine channel instead, e.g. Ars Technica's RSS feed, with items labelled text_source=feed-lead. robots.txt and Crawl-delay are honoured, and the crawler identifies itself honestly. For sources whose terms forbid automation (Crunchbase, G2, Glassdoor) the production path is their licensed API.

6. Fault tolerance and operations

FailureBehaviour
Worker crash mid-runKeyed upserts plus resume-by-key: the rerun skips stored items. Unfinished freshness claims expire with their lease and are re-claimed by another node.
One bad page / parser errorIsolated per item, counted by reason in the run summary; the crawl continues.
Source down or feed failingRetries with backoff; a failed run is not recorded as the baseline for "new since last run", so no items are wrongly judged on the next run.
Provider outage / quota exhaustedProvider cooldown, fall through the LLM chain; if all fail, the item is recorded as not extractable and never stored half-extracted (a production queue would re-deliver it later).
Site starts blockingBlock classified, host slowed, circuit opens with doubling cool-down; the blocked-host rate is a metric to alert on.
Bad or ambiguous dataGrounding gate, three-valued freshness, evidence-backed maker names, website-based entity identity: the pipeline prefers an empty field or a dropped record to a guess, and every value keeps its source URL.

Observability. Structured JSON logs (structlog) with per-source, per-host and per-provider counters (fetched, stored, stale, uncertain, near-duplicate, blocked by kind, retries by status, provider fall-throughs). Every run ends with a machine-readable summary, which is the basis for dashboards and alerts in production. 249 offline tests cover the orchestrator (fallback, 413 shrink, 429 cooldown, repair), chunker, date parser, freshness heuristics, deduplication races, entity resolution and the anti-bot tiers, with mocked network and fake LLM providers.
